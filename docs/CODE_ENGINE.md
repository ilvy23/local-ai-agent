# `agent code` — the new coding engine vs. the old one (`--classic`)

Evidence legend: 🟢 green = seen working in a real run on the 27B · 🟡 yellow = checked against the live server with short probes (not a full run) · 🔵 blue = covered by unit tests only (fake model) · ⚪ not verified / not built.
Tests: 1787 pass (1 skipped). Real runs so far: a todo app (tests pass), a one-file module (`worldmap.py`), a long extension of a text-adventure game, and a 10-stage `inventory` package (19 files, 71 tests) built in one saved session over three processes with a deliberately tiny 16k window (2026-10-11, see "Long runs").

## Start it

```bash
agent code                          # interactive session in the current project (or: menu → Code → Coding session)
agent code "add a /health route"    # one task, then exit
agent code-policy list              # which repos may do what
agent code sessions                 # saved sessions of all folders (--here, --delete ID, --prune DAYS)
agent code --resume [ID]            # continue one (the folder's latest, or by id prefix - it opens in its own folder)
```

## Speed and model

| | old (`--classic`) | new |
|---|---|---|
| model | a 7B coder | the 27B chat model (per repo: `/model`) 🟢 |
| context | 16k | **98k, fully on the GPUs** 🟢 |
| writing speed | ~ model dependent | **41–48 tok/s** in agent runs 🟢 (benchmark: prose 35, code 57, file rewrite 61) |
| reasoning pass per step | always | off; switched on only after a failed check or when stuck 🔵 |
| tool call per step | one | up to four (extra calls are reported back, not silently dropped); `read_files` batches reads 🔵 |
| runaway generation | runs to the token cap | the reply is **streamed**; text that turns into one block repeated over 8k chars is stopped and re-rolled (bounded like empty replies). The model writes its calls as JSON text, so this also covers a looping `write_file` 🟡 (abort stops the server at once; the engine's streamed call replayed on a saved session). Native tool calls are buffered by Ollama, so for them only the 32k cap applies. A reply cut off by the cap is reported as such 🔵 |
| Ollama error / dropped connection | turn ends | retried once with the same state, then stops with the error text and keeps everything; the window only shrinks when the error says out-of-memory (a plain 500 used to shrink it and force a reload) 🔵 |

## Editing

| | old | new |
|---|---|---|
| change a file | rewrite the whole file or exact `replace_in_file` | `edit_file` (tolerant to whitespace/indentation, several edits atomically) 🟢, `apply_patch` (unified diff, `*** Update File` blocks, header-less with `path=`) 🔵 |
| big new file | any size | **always accepted** (up to 120k chars), advice comes after, never a refusal 🟢 (579-line `dialogue.py` in one go); the old "≤ 14k chars per write" advice is gone from the prompt and the tool description |
| very large file | — | `append_file` in chunks; tiny one-line appends are cut off 🔵 |
| writes | in place | atomic (temp file + rename: Ctrl-C or a full disk leaves the old file whole), mode and CRLF line endings kept, binary files never edited (an overwrite moves the old one to the trash) 🔵 |
| read-only files | overwritten | never written, moved or deleted; the model is told not to retry, a big generated file is kept in `.scratch/unsaved/` 🔵 |
| syntax check on every write | only at the end of a round | **right after each write**, with the exact line and a hint (py, json, toml, yaml, sh, js) 🟢 |
| cross-module check | — | **XREF**: invented methods, wrong imports, wrong argument counts against sibling modules 🔵 |
| failing command | raw output | traceback **plus the source lines it points at**; long pytest reports condensed to the failures 🔵 |

## Verification and honesty

| | old | new |
|---|---|---|
| check before "done" | check ladder, coverage gate, LLM judge of the diff | the **harness** runs `py_compile` + the project's test command (detected, or routed through `uv run --with pytest` on this system); skips a command the model already ran 🔵 |
| acceptance list | — | harness-owned checklist, `mark_done(ids=[…], evidence)` 🟢 |
| unsupported claims | — | deterministic, no model call: an answer that says it works/was tested while nothing but a compile check ran since the last edit is sent back once 🔵 (the earlier model-based check also evicted the conversation from the server's prompt cache: re-reading a 27k-token prompt took ~38 s 🟡) |
| "not done" reminders | — | syntax ≤2, failed checks ≤2, acceptance list ≤1, claims ≤1, and **at most 4 in total** per prompt; then the answer is accepted and marked unverified 🔵 |
| existing tests protected from edits | **yes** (read-only) | **no** — not carried over ⚪ |
| coverage gate / LLM diff judge | yes | **no** — not carried over |
| auto-install missing packages | yes (pip) | no, by design: this system's python is read-only; tests go through `uv` |
| sandbox in a git worktree | yes | no: it edits in place, with `/undo` and a git checkpoint ref before the first edit 🔵 |

## Context (long runs)

| | old | new |
|---|---|---|
| tool results | cut to 6000 chars | cut only when needed |
| keeping the prompt prefix stable (server cache) | no | yes: prefill of a 30k-token prompt takes 0.2–0.8 s on the next step 🟢 |
| trimming old tool output | — | once, in bulk, at 72 % of the window (`MASK_AT`), then not again until it grew by 15 %; compaction at 80 %, hard trim at 92 %. A file read keeps its **outline** and the range to re-read (so it is not re-read blindly) 🟢. **Inside a stage** the budget is `min(window, stage cap)`: ONE batch masks the old read/search/run/web results, oldest first (a contiguous old prefix keeps the server's KV cache valid up to the first changed message), until the estimate is <= `stage_mask_target` x cap; it always keeps the newest result and a working set of the newest results up to `mask_keep_tokens` x cap (never edit results, the brief, the stage goal, the verified state; `mask_keep_turns` is only a floor of 2 turns). A trigger batch at `stage_mask_at` x cap runs only if it frees >= 25 % of the prompt (`stage_mask_skipped` reason `low_gain`); the cap only ends the segment if the estimate after the forced batch is still over it (event `stage_mask`). Thrash guard: a batch needed again within 6 steps, or two batches in a row within `stage_mask_window` steps that each freed < 20 %, stop masking and end the segment with `stage_cap` (reasons `again_within_steps`, `two_fruitless_batches`): one clean restart costs one cache invalidation 🟢. Measured: with the old keep-6-turns rule batches freed ~3k of 29-34k tokens, 11 big prefills = 135 s in 8 min (prefill 46 % of model time) 🟢. A mask re-reads the whole prompt (measured: 50–77 s for ~50k tokens), so one that frees < 15 % of the window is skipped and compaction takes over 🟢 (`mask_skipped` events; one older run had paid four 12k-token masks in 59 steps, ~250 s of prefill) |
| compaction | — | at 68 %: a work log **plus a ledger checked against the disk** (files, syntax, commands with exit codes), the **live acceptance list** and the project notes of the session 🟢 (8 compactions in the 16k run; the log kept exact names, open items in order and pitfalls). The log is written **in place**: the conversation model gets its own (cached) conversation plus one instruction, so only the log is generated - in-place calls had 1.3–2.8 s prefill for 11–13k-token prompts, ~25 s in total 🟢. Falls back to the separate summary call when the reply is not a log or there is no room left to write it 🟢 (seen once at 97 % fill; the room check is 🔵) |
| old turns | — | folded into the log when they fill 45 % of the window at the start of a prompt 🟢; a log folded into the head is merged by the next compaction instead of staying there for good 🟢 (before: two 11k-char logs in a 16k window, compaction could not get below 68 %), and requests still visible verbatim are not copied into the log again 🔵 |
| what happened to my context? | invisible | `~/.local/state/agent/code-events.jsonl` + `/events` (steps, prefill/decode seconds, masks, compactions, loops) 🟢 |
| window nearly full | — | if it is still ≥85 % after compaction (compaction is a model call and can fail), old tool output is trimmed hard without a model 🟢 - only when that frees ≥ 8k chars or the window is ≥ 95 % full (seen live: 500-char trims every step, each one a cache miss of ~17 s) 🔵; a failed compaction is retried only after 5 % more growth 🔵 |
| session autosave | — | before every model call and after every prompt, written atomically 🟢 (a `kill -9` mid-prompt resumed cleanly) |

## Freedom and safety (per repo, `/mode`, `/allow`, `code-policy`)

| | old | new |
|---|---|---|
| permission levels | one sandbox | `ask` / `medium` / `auto` per folder 🟢 |
| allow / deny command patterns, network, installs, commit policy, step budget, think mode, model, ctx | — | yes, saved in `~/.config/agent/code-policy.json` 🔵 |
| paths outside the repo | system-path blocklist | always asked (or refused without a terminal, never repeated) 🟢 |
| two agents in one folder | possible | one session per folder (kernel lock) 🔵 — this corrupted a test run before |
| commands | plain subprocess | own process group, stdin closed unless fed, output to a temp file (stopped above 8 MB); on timeout, Ctrl-C or exit the whole group is killed - background children and pipe-holding grandchildren cannot outlive the command or hang the harness 🔵 |
| housekeeping in `auto` repos | every `rm`/copy to /tmp asked | `rm` only in disposable folders (.scratch, build, …) or the user's own /tmp/<name>; cp/mv only into those or to a *new* repo path (never over an existing file); `cd` is followed; `$`, `&`, newlines, backslashes, globs, `..`, unknown flags are refused; symlinks resolved. Real repo files: `delete_file`/`move_file` (recoverable) 🔵 |
| nobody at the terminal | — | every approval (also for the final checks) is refused at once without a terminal on stdin, so a scripted run never waits for input 🔵 |
| only your global file grants anything | — | a policy file inside a repo is never read |

Files the agent itself wrote or that a `run` command created (a data file like `todos.json`) may be removed with a plain `rm`/`unlink` in `auto` mode, and in `medium` mode when a command created them (never recursive, never a folder, glob or `.git`; a file that already existed before is the user's and still asks). In shell commands a plain `cd <subfolder>` / `cd ..` inside a `&&`/`;` chain is followed, so `cd .scratch && python ../main.py` stays inside the repo; an unclear `cd` (variable, substitution) still asks.

## Not stuck in loops

| | old | new |
|---|---|---|
| same call 7× | stall → stop | the same call with the same outcome (timings ignored; for `run` / `search` also a nearly identical command, see below) within the last 16 calls - not only back to back, so 3-step cycles count - climbs a ladder: 2nd repeat → one line appended to the tool result (`Same result as your last call; it will not change.`); 3rd → one hint that lists the last 3 attempts, the earlier copies are removed from the context, and one bounded reasoning pass; 4th → the segment ends as `loop` (the supervisor restarts it in a fresh context). A successful write starts a fresh count 🔵 (the earlier 3×/6× form was 🟢 in the old back-to-back version; the near-identical playthrough that slipped through is from a real run) |
| same error repeated, cycles | — | the same hint (error wording) 🟢 |
| empty replies | re-asked forever | 2 silent re-rolls, then a note, stop after 6 🔵 (the real incident ran 291×) |
| garbled tool calls (`{"tool":…<parameter=…>`) | lost | rescued and executed 🟢 |
| arguments as text instead of a list | error | repaired (JSON, raw newlines, Python literals), else an error **with an example call** 🔵 |
| endless reading | — | one nudge at 10 steps / 700 lines without writing, once more at twice that (was two separate messages back to back) 🟢 |
| same problem twice | — | automatic web lookup (respects `AGENT_AUTO_LOOKUP=0` / `autonomy.web_lookup`, result capped) 🟢 |

Near-duplicates and dead ends. For `run` and `search` two calls count as the same attempt when the word sets of their texts (lower-case identifiers; quotes, punctuation and bare numbers ignored; for `python -c` and heredoc bodies the whole body) overlap by at least 0.8 (Jaccard) within the last 10 calls, or when the older whole-call similarity matches. They count toward the same repeat counter as exact duplicates only when the outcome is also equal: the same result, or two errors with the same first error line (the final line of a Python traceback, a pytest `FAILED id`, else the first non-exit line). A different output, or a different failing test, never counts. Three more one-line facts are appended to a tool result and never cost a model call: on the second identical error, `Traceback ends at <file>:<line> - open it with read_file/show_symbol instead of re-running.` (last frame inside the repo) or the failing pytest id; and, once per session, when `printf ... | python3 <script>` (or `stdin`) is repeated three times and the output is only prompts, a hint to drive the program from a script. Every loop detection (hint or stop) is also written to the DEAD ENDS ledger in the engine: tool, command head and first outcome line (120 characters each), count, the newest 12, one entry per attempt. It is saved with the session (`engine_state.dead_ends`; old sessions load with an empty ledger) and shown as `DEAD ENDS (already tried, same result - do not repeat)` in the VERIFIED STATE (after the open acceptance items, at most 600 characters), in the fresh context of a stage or supervisor segment, and in the resume note, so a restart after a loop stop knows what already failed. An entry is removed when the file it concerned is edited, or when a later attempt of the same signature succeeds (an error entry) or gives a different result (a "same" entry).

## Stages, autopilot and speed diagnostics

All 🔵: built and tested with a fake model; no real run has measured them yet, so this section makes no speed claims.

```bash
agent code --stages "a big task"        # split into stages (headings / lists of the task), each in a fresh, small context
agent code --autopilot "a big task"     # a supervisor runs the stages and restarts stopped ones with graded recovery (implies stages)
agent code --autopilot --resume         # continue the saved stage plan
agent code state [--folder PATH]        # the verified state of a folder, measured now (tests, checks, open items, files); no model
agent code time [--session ID] [--since 2h]   # where the time of a run went, from the event log; no model
```

- `/state` (in the session): the same verified state as `agent code state`, for the current session.
- `/why-slow` (in the session): the time breakdown of this session and up to 3 causes.
- `agent code time`: without `--session` it reads the latest session of `~/.local/state/agent/code-events.jsonl` (`AGENT_CODE_EVENTS` overrides the path); `--session` takes an id or a prefix, `--since` a span (`30m`, `2h`, `1d`; a bare number is minutes) over all sessions. Output: wall time and its shares (prefill, generation, tools with the part spent in test runs, waiting for the server or the model load, other), steps/min, mean and peak prompt tokens, number of segments and stages, then the causes. Every number comes from the event log; with no obvious problem the only line is `no obvious bottleneck`.
- The causes are rule based (thresholds in `timing.py`): prefill above 25 % of the wall time (with a mean prompt above 30k tokens it points at `coding.stage_prompt_cap` / `--stages`), fewer than 6 steps/min, more than half of the tool calls read-only, tool time dominated by test runs, thinking steps producing a large share of the generated tokens, waiting on the server.
- Autopilot rule from the same measurement: if prefill is more than `coding.prefill_end_share` (default `0.5`, `0` = off) of the last 10 minutes of the current segment (at least 5 measured steps), the segment ends at the next step boundary and the same stage continues in a fresh context. This is logged as the decision `fresh_context` and does not count as an unproductive segment. The final autopilot report (`.scratch/autopilot-report.md`) has a `speed (measured)` section with the breakdown and causes.
- `scripts/prefix_report.py [--repo PATH] [--task TEXT] [--top N]` measures the fixed prompt prefix without a model (temp state only; `--repo` is copied first): token estimates (characters / 3.2) of the system prompt, PROJECT block, every tool schema, brief card, repo map, project memory, stage goal / notes, dead ends and verified state, sorted by size, then a stability check (build twice with the clock moved two hours; a stage restart after a new file, a saved note and a few steps) and a pattern scan, and the list of prefix-cache breakers (exit 1 when there is one). Sample repo, 2026-10-17: about 5.9k tokens, of which 3.2k are the 26 tool schemas and 0.9k the system prompt. Test: `tests/test_codeagent_prefix.py`.
- `scripts/speed_trial.py FOLDER "task" [--cap 16000]` runs `agent code --autopilot --stages` as a subprocess with a small stage prompt cap (`AGENT_CODE_STAGE_PROMPT_CAP` for that process only), prints the breakdown of that run and PASS / FAIL against flags (`--max-prefill 0.25`, `--min-steps-per-min 6`, steps/min only judged while the peak prompt is at most `--peak-limit 30000`). `--dry-run EVENTS_FILE` only parses an events file. It uses the model, so it is not part of the tests.
- Exit codes of `agent code --autopilot`: `0` all stages done, `2` needs a human (a stage is blocked, idle limit, or the server did not come back), `3` partial (some stages done, others not), `130` stopped by the user (Ctrl-C; the session is saved).

## Questions, help and plain-prompt splitting

- Intake (`intake.py`): before a new, non-trivial task on a terminal, one non-thinking call of the main model (not the small background model, so the main model is not evicted from the GPU) reads the task and the repo profile and returns up to 3 short questions, or none when the task or the repo already answers. You answer one line per question: Enter or `s` skips, `go` stops asking. The answers are appended to the task as `Clarifications from the user:` (a skipped one reads `your call (state your assumption in the summary)`) and are pinned in the brief card, so they survive compaction and stages. Even a short vague prompt (12 characters or more, e.g. `make a todo app`) gets it, because those are the ambiguous ones; the model decides and returns no questions for a clear task. For a greenfield task it asks about the 1-3 decisions that most change the result (language/stack, CLI/GUI/web, persistence, scope). It is skipped when the repo already has code and the task names something concrete in it (a file with an extension, a symbol, an error text, `fix` / `bug`); an empty repo or greenfield wording (`make / build / create / write me a ...`) always runs it. Not asked for slash commands, resumed stage plans, a task text already seen in the session, or when no terminal is attached (so never in an unattended `--autopilot` run).
- Web discipline: the model's own `web_search` / `web_fetch` calls are answered with one fixed line ("Web lookup not needed yet ...") unless the task text mentions http, www, search, online, docs, documentation, latest, current version, look up or google, or at least 2 tool runs failed since the last user prompt; the automatic "same problem twice" lookup is not affected.
- `ask_user(question)`: the model can ask ONE short question when blocked (3 per prompt or stage, then it is told to decide itself). Without a terminal it returns at once that nobody is available and the model states its assumption in the final summary. Allowed in every mode; counts as neither a look nor an act. On the second `loop` stop of a stage the autopilot supervisor asks you once for a hint (Enter = continue) when a terminal is attached and passes the answer in the restart note.
- A task without structure is split by one main-model call (`stage_split_with_model`): one stage for a coherent change, 2-6 only for separable deliverables. The answer is validated strictly (2-8 stages, goal 20-1200 characters, no duplicates; otherwise one stage) and cached per task text in the session, so a resume does not ask again. With two or more stages their titles are printed first.

## Configuration (`coding.*`)

All keys live under `coding` in the agent config (`config.yaml`). Every key is optional; the default is what the engine does without it. A broken value (not a number where a number is expected) falls back to the default. The numeric limits below read the module constant as their default (`agent/codeagent/engine.py`, `lookact.py`).

A stage that keeps ending at the prompt cap is usually too big for one context: every fresh context reads the same large files again. When it ends there for the `coding.resplit_after_caps`-th time (default 2), the engine asks the main model once for 2-6 disjoint sub-stages that name their files and skip what the stage already changed; if that answer is unusable, it groups the files named in the stage goal (or the files read most) into parts of at most about 600 lines. The sub-stages replace the stage in the plan (ids renumbered, `parent` set, a sub-stage is never split again), the event `stage_resplit` is logged, and each sub-stage starts with a LARGE FILES hint that lists its files above 12000 characters and asks for line-range reads only. If fewer than two parts result, the stage goes on unchanged. The same split runs at stage start for broad goals (`broad_split`, once per stage, only for stages that were not split yet).

Named-file scope and line-range parts (`stages.py`, `cursor.py`): measured live, "In dialogue.py, rewrite the spoken lines ... work through the whole file section by section" (687 lines) fired the broad rule and was split into parts per REPO FILE (main.py, PLAN.md, ...), so dialogue.py stayed untouched. Now `named_files` derives the files a stage's title + goal names: an explicit file name or path that exists in the repo (whole word, not inside a longer name), or "the X module" when X.py exists, in the order of the text (the `Overall task:` head of a sub-stage does not count). When 1-3 files are named, a re-split (broad or cap-based) may only use those files: the model prompt lists only them (`REPO FILES`) and an answer that names another file is rejected, the deterministic fallback groups only them. More than 3 names, no name, or a feature goal ("Add ...", "Create ...") keep the old behaviour. A named file above `coding.range_split_lines` is split with no model call into consecutive line-range parts (target 140 lines, each cut moves at most 25 lines to the nearest top-level `def`/`class` of a .py file, else to a line after a blank line; at most 8 parts over all named files, files in the order named, a smaller named file stays one whole-file part; a stage that already finished lines 1..n from the start continues at n+1). Titles are `Part 2/5: dialogue.py lines 151-300`, the goal is `Work ONLY on dialogue.py lines 151-300 (the rest of the file is handled by other parts). <original instruction>`, scope is the file, and `Stage.lines` = (first, last) and `Stage.lines_total` (the file length the range was valid for) are saved with the session (absent in an old session = no range). The broad rule does not fire for a named file that is not above the threshold.

A ranged part is range-aware everywhere: the STAGE CURSOR section and the `Continue at:` note read `dialogue.py lines 151-300: next unedited line 161` (or `done`), the start notes say `read dialogue.py lines 151-300 only (start/end)`, and the scope gate (and the supervisor's harness-close rule) wants a recorded change that overlaps the range, or a `mark_done` / `project_note` waiver that names the file (a shell write the cursor never saw counts when nothing at all was recorded for the file). Earlier parts add or remove lines, so `cursor.sync_range` follows them: the difference between the file length now and `lines_total` moves both ends of a part that has written nothing yet and only the end of a part that already wrote (title and goal are rewritten to the current numbers; later parts named in the `later stages` note keep their planned numbers until they start). Reading another file during a ranged part gives one note per segment (`Outside this part: only dialogue.py lines 1-150 are yours`) and counts `coding.out_of_scope_read_weight` steps toward the look pause; the event `out_of_scope_read` is logged for each such read.

Deterministic range plan (`stages.split(..., root=)`, `stages.range_plan`): measured live, the same prompt a second time (after the range split was fixed) got ONE stage from the model-based split, so `split()` returned `single`, `run_task_staged` returned None and the prompt ran as a plain one-shot turn on the 687-line file (9 searches, 7 reads, 12 runs, zero edits, loop abort after 4m48s). The staging decision no longer depends on a model answer for this class of task. Before the structure and model splits, `split()` checks the task text: it names 1-3 existing files (`named_files`), at least one has more lines than `coding.range_split_lines`, it has editing-by-passes intent (`cursor.INTENT` / remove words) and does not open with a creation verb. Then it returns the range plan directly, source `ranges`, with NO model call: the parts `_range_substages` builds (`Part k/n: file lines a-b`, scope = the file, no other repo file) plus ONE last normal stage (no scope) `Run the tests and fix what YOUR rewrites broke` when the task mentions tests or the repo has test files. If the task text itself has headings / stage headers, those stages are replaced by the range plan only when each of them names every big file (the range plan is finer); stages about other files keep the structure plan. Small named file, creation prompt, no named file or no editing intent: unchanged (structure, then model, then single). `coding.stages: auto` treats a `ranges` plan as staged; `off` still means no stages; `range_split_lines: 0` turns the rule off. The autopilot predicate `should_autopilot(task, cfg, root)` is also true for such a short task (< 600 chars, < 3 bullets) when `stages.range_job` says so (names + file sizes only, no model call); the REPL applies the same rule without changing the permission mode. The intake does not ask anything: `looks_specific` already accepts a task with a named file in a repo with code. Ranged parts get direct-to-edit pressure: the begin_stage note adds "Start by reading lines a-b of <file> (read_file path start=a end=b) and rewrite them immediately in place with replace_lines/edit_file; do not search the rest of the repository first; tests are run once at the end.", and the first `coding.stray_looks` (default 8) `search` / read-only `run` / `list_dir` calls of the part count `coding.stray_look_weight` (default 2) steps toward the look pause, also during the 6 free orientation steps (reading the range itself and edits are untouched), so the read-pause wall comes earlier for stray investigation.

A stage has a hard budget (`stage_max_minutes`, `stage_max_steps`), measured by the harness over all its segments and resumes (`spent_s`, `spent_steps`, `real_edits` are saved with the stage). At a segment boundary the supervisor blocks a stage with the reason `budget: <min> / <steps> steps / <edits> edits` when time or steps are used up and its real edits do not keep pace (`stage_min_edits_per_100_steps`); a stage that keeps editing at a healthy rate may use up to 3x the budget, one that mostly investigates is cut at the base budget (this is what stops a part that chases failing tests of other parts through ever-new scratch scripts). A budget-blocked stage is not dead: when every other stage is done or blocked, the supervisor makes ONE retry round with half a budget and the note "Previous attempt used the whole budget without finishing ... Decide quickly: finish what is left of THIS part, or state with mark_done evidence that nothing is left."; a second budget block is final, is listed under NOT VERIFIED in the autopilot report with its numbers and ends the run with exit code 3 (partial); the events are `stage_budget` (`id`, `spent_s`, `steps`, `edits`, `action` = `block` / `retry` / `final`). A sub-stage whose scope is changed or waived, with no newly red test and no real edit in its last 2 segments, is closed by the harness ("closed by the harness: scope satisfied, no new test failures, no edits in the last 2 segments") as soon as it has used 60% of its budget, even if the model never said it was done.

Family and run-spam guards (`loopguard.FamilyGuard`): the same-outcome loop guard misses a model that runs the same kind of look (e.g. 30 `python3 -c "..."` over one test file) whose output differs slightly every time, so calls are also counted by kind, and `run` calls that changed nothing are counted per window. A successful edit (also a shell one) is the only reset; test runs whose summary line changed since the previous test run do not count, nothing fires in the first 6 calls of a stage or within 6 calls after an edit, and a plain `python3 main.py` has no family (only run-spam watches it). Both guards are deterministic, keep no saved state, and never force a reasoning pass.

Pattern guards (`loopguard.PatternGuard`, after the family guard and the repeat ladder, never a model call, never `think_steps`): three counters that need no equal outcome and are reset by a real edit, like the others. Nothing fires in the first 6 calls of a stage or within 6 calls after an edit; the state is not saved. (1) `same_tool`: the same tool name `same_tool_note` times in a row, whatever the arguments (12 `search` calls with new patterns, 12 different `curl` commands, 12 failing `edit_file` calls). Not counted: reads of different files, one file read in distinct ranges (the read tools count only a call that overlaps lines already read), successful writes, read-only shell commands, commands that changed files, a test run whose summary changed. (2) `alternating`: the tail of the last 16 calls is a pattern of 2 or 3 identical calls repeated (`alt_note` rounds); a test run alternating with an edit never counts because an edit clears the history. (3) `read_window`: 4 re-reads among the last 15 calls (a note), 8 (stop); it sees what `look_block_at` cannot, because a `run` between two reads ends that streak (measured: 229 reads against 32 edits). One voice per call: when the family guard, the repeat ladder or (for `run`/`search`) an earlier family note already spoke, a pattern note is dropped; the stops always stand. A stop writes a DEAD END (`investigated without editing`).

Streaming repetition (`loopguard.ChantDetector`, one instance per kind of a model call, `content` and `thinking` separately): every 100 streamed characters the last 50 characters are looked up in the last 4000. Clustered: `chant_hits` (reply, 14) / `chant_think_hits` (thinking, 10) occurrences, each within 75 characters of the previous one (a short sentence said over and over, cut after about 400-1000 characters). Periodic: a longer unit at one equal stride, 5 occurrences (3 in thinking and 4 in a reply when the unit is 800+ characters) and the whole stretch exactly periodic over at least 1000 (thinking) / 2000 (reply) characters. A chunk with fewer than 5 (thinking) / 8 (reply) distinct characters (dividers, rows of zeros) never counts. The abort uses the existing path (`degenerate` event, `the reply started repeating itself`, the reply is discarded and re-rolled, a thinking pass is switched off); `engine.repeating` (one block over 8000 characters) stays as the backstop for units longer than the window.

Chunk protocol and stage cursor (`cursor.py`): a stage that names files (its scope, else the files listed with it) and whose title or goal says rewrite / rephrase / polish / simplify / improve / clean up / translate / refactor / rename / document (or the German stems) gets one `WORKING METHOD` block in its start notes: go through the files in order, read at most 80 lines, rewrite them right away, then take the next 80; no survey or text dumps first; run the tests once after each file. Every file-tool write of a stage (`replace_lines`, `edit_file`, `insert_after`, `write_file`, `append_file`, `apply_patch`) is recorded in `Stage.edited` as line ranges in the file's current numbering (overlapping and adjacent ranges are merged; a write that changes the line count moves the later ranges; shell writes are not recorded). The ranges are saved with the session (a session without them loads as empty). From them the start notes carry `Continue at: story.py line 201 (edited 1-200 of 406); dialogue.py not started`, and VERIFIED STATE gets a `STAGE CURSOR` section (at most 500 characters, after OPEN ITEMS, so it is dropped before them when the block is too big). In a chunk stage reading is paused after `coding.chunk_look_block` read/search steps in a row (read-only `run` commands count as reads), and the pause message says e.g. `Rewrite lines 201-280 of story.py now (read them first if needed).` The scope gate is unchanged; the cursor only shows which files are not started.

Scope gate: a sub-stage names its files. The stage is not green until each of them was changed during the stage or the model waived it by calling `mark_done` / `project_note` with a text that names the file (its basename) and says it needs no change. Otherwise the final gate sends the model back (counted with the other gate nudges); when they are spent the segment ends as `gate` with `NOT VERIFIED: files not handled: a.py, b.py`. Stages without files are not affected.

A Python write that removes a def / class / assignment name which other `.py` files still mention gets one more line in its result: `Removed <name> but it is still used in: a.py:12, b.py:40` (where_used, no model call).

Path jail: private and system locations (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config`, `~/.local/share` except `uv`, shell history and rc files, `/etc/shadow`, `/etc/ssh`, `/root`, `/boot`, `/sys`, `/proc`, `/dev`, other users' homes, the home folder itself, ...) are refused at once, in file tools and in shell commands (`~`, `$HOME`, `..` and symlinks are resolved first). The model gets one line, `NO: <path> is private/system; work only inside the repo (scratch in .scratch/).`, nobody is asked, and a repeated identical call gets the identical answer and counts toward the loop guard.
Sibling projects and other outside paths still ask as before.

Lifetime of the limits: `gate_consecutive`, `gate_nudges`, `announce_max`, the per-check return count and `auto_extend_max` do not last for a whole session. They count per finish attempt / stage segment and start again after real progress (`supervisor.measure_progress`: changed content of a written project file, or more green checks / confirmed items / passing test runs). Unusable replies (unreadable tool calls, output cut off, empty or thinking-only replies) are counted in a row (`malformed_abort`, one short reminder per streak) and start again after any readable tool call or real answer. A pure-text answer while acceptance items are open (or, in a staged run, files have errors) is sent back whatever its wording; only without a plan or stage plan the wording heuristic decides. Stop reason `gate` is treated like `loop` by stages and supervisor (unproductive unless progress).

`coding.protect` guards the player's own data (a save file the human plays with and must keep writing), independent of file modes. File-tool writes (write, append, edit, replace_lines, insert_after, apply_patch, move, delete) to a matching path are refused with "is protected (the player's own data)" and never count as an action. Before every shell command that is not read-only the protected files are snapshotted (content, mode, mtime; 5 MB total); a command that changed or removed one gets it restored byte for byte plus a note, and a protected file it created is deleted again. Reads stay allowed, and nothing below a `.scratch/` folder is protected, so copies there (`.scratch/x/save.json`) are where the model experiments; note that a pattern such as `savegame*` also matches source files like `savegame.py`.

Loop detection was extended with ideas of qwen-code's `loopDetectionService.ts` (https://github.com/QwenLM/qwen-code/blob/main/packages/core/src/services/loopDetectionService.ts, Apache-2.0, plus its test file). Clean-room reimplementation: the upstream source was read for its detectors and constants only; no code was copied, structure and names are our own (`loopguard.PatternGuard`, `loopguard.ChantDetector`). **Measure the fixed prefix** (pi `packages/coding-agent/src/core/system-prompt.ts` / `tools/*.ts`, survey rank 6): not ported as slimming; only measured with `scripts/prefix_report.py` (see "Stages, autopilot and speed diagnostics"). **Gate cap = consecutive blocks without a tool call** (Claude Code hooks guide, section "Stop hook hits the block cap", https://code.claude.com/docs/en/hooks-guide). Verified upstream (the page text was fetched and the passage located): a Stop hook may block, but Claude Code overrides it after it blocks eight times in a row with no tool call from Claude in between; the hook receives `stop_hook_active`. Only this one sentence and the field name were taken; no Claude Code source was consulted. Reimplementation in `CodeEngine`: `_gate_streak` counts final-gate nudges (syntax, static, verify, plan, claims, scope and the checks gate) in a row; any tool call that `lookact.classify` does not call neutral (reads, writes, runs; not `mark_done` / `project_note` / `add_check` / `ask_user` / `write_prose` / web) resets it. `coding.gate_consecutive` (default 4) is the cap: when the streak reaches it the answer is let through, with open acceptance items as `stopped='gate'` and NOT VERIFIED, and a failing check is listed as NOT VERIFIED instead of sent back. `coding.gate_nudges` stays as the per-attempt hard ceiling, default 12 (3x the old 4); progress still resets it. Differences: the number is 4, not 8 (a local 27B that only answers with text does not change its mind after 4 nudges); the per-gate caps (syntax 2, static 2, verify 2, plan 1, claims 1, scope 2, `CHECK_RETURNS` per check) are unchanged, so a model that keeps acting can still run into those; announce continuations (`announce_max`, never twice without a tool step) do not count into the streak. Tests: `tests/test_codeagent_limits.py` (last block); changed on purpose: `test_defaults_are_unchanged_without_overrides` (`MAX_GATE_NUDGES` 4 -> 12, new `GATE_CONSECUTIVE == 4`) and the config test (`gate_consecutive` falls back to its default on a broken value).

**Edit matcher levels** (opencode `packages/opencode/src/tool/edit.ts` at tag v1.0.0, https://raw.githubusercontent.com/sst/opencode/v1.0.0/packages/opencode/src/tool/edit.ts, MIT). Verified upstream through a summarising fetch tool (not byte-checked): nine replacers in this order: Simple (exact), LineTrimmed, BlockAnchor (3+ lines, first and last line trimmed, middle by Levenshtein, threshold 0.0 for one candidate and 0.3 for several), WhitespaceNormalized, IndentationFlexible, EscapeNormalized, TrimmedBoundary, ContextAware (3+ lines, at least 50% of the middle lines similar), MultiOccurrence; a replacer that yields several matches makes the edit fail with a request for more context. The typographic quote/dash/space level is NOT in v1.0.0; it exists in the `dev` rewrite (survey O1). Clean-room reimplementation in `edits.replace_once`: exact; whitespace/indentation-tolerant line match (unchanged; it already ignores indentation and no-break spaces, so the requested "indentation-flexible" level is covered by it and reports `whitespace-tolerant`); NEW typographic level (curly single/double quotes, dashes, `…`, space variants folded on both sides, also inside a line, then the same line-wise with whitespace folded; a match never cuts a widened `…`); NEW block anchor (3+ lines, first and last line equal after folding, the nearest closing line, middle `difflib.SequenceMatcher` ratio >= 0.7, block may be a little longer or shorter than the search, anchors at least 8 characters together). The new levels need exactly ONE candidate; 2+ candidates (also with `replace_all`) are refused with the line numbers. The replacement is written as the model gave it (the typographic fold is for comparing only). The tool result names the level: `edited f.py: 1 edit(s) applied (matched ignoring typographic quotes/dashes).` or `(matched by its first and last line, the middle lines differ (similarity 0.82, lines 4-9))`. Different from upstream: threshold 0.7 for a single candidate instead of 0.0 (a wrong block is worse than a failed edit), no escape / trimmed-boundary / context-aware levels. `replace_lines` with `expect=#hash` and `apply_patch` do not use these levels. Tests: `tests/test_codeagent_edits.py` (last two blocks).

**New diagnostics only** (Claude Code, code-intelligence plugins page, https://code.claude.com/docs/en/plugins/code-intelligence). Verified upstream (fetched): after each edit the conversation shows `Found N new diagnostic issues`; Claude gets the errors the language server reports for a file it edited. How "new" is decided is not documented there; the baseline rule below is ours. `CodeTools._static_note` now compares the problems of the written text with those of the file as it was BEFORE the write (`_bookkeep` remembers the text; for chunked `append_file` the last checked state is used) as sets of `(message without line numbers, whitespace-normalised content of the pointed-at line)` (`static.signatures`), so shifted lines do not look new. The note lists new problems under the usual STATIC CHECK header and adds one line `N earlier issues in this file unchanged`; a first write, or a file without a known earlier state, shows everything. Syntax errors are not part of this (SYNTAX GATE FAILED is always shown). `static_bad` and the final gate still hold and report the WHOLE list: the diff is for the note only, a file the model touched is not green while it still has a problem. Tests: `tests/test_codeagent_static.py` (last block).

**Duplicate-block protection** (own design, no upstream). Seen live (15-minute run on a prose-heavy `dialogue.py`, 687 lines): `replace_lines` was given an end line that was too small, so the new, longer data blocks (`ELLA_OPEN`, `ELLA_CHAPTER`, `ELLA_TREE`, 141 lines in one insertion) were inserted in front of the old ones; Python accepted the second assignment, all tests stayed green and the file grew to 812 lines. Three deterministic checks, no model call: (1) `static.duplicate_bindings` (part of `static.check`, so it is a new-diagnostics-only STATIC CHECK finding and lands in `static_bad`): a module-level name (def, class, plain or annotated assignment, also a data dict) bound twice at the top level with no read of it in between -> `NAME is defined twice at module level (line a and line b) - the first definition is dead. If you rewrote a block with replace_lines, your end line was too small ...`. Exempt: bindings inside if / try / for / with, `x = x + [...]`, `x += ...`, `x.update(...)` and any other read (a function that reads the name counts), `global` rebinding, decorated defs (overload, property setters, register), a constant first value (`X = None`), `_` and dunder names, dynamic modules (`import *`, `globals()`). Two plain defs stay with `duplicate_defs`. (2) `edits.duplicate_block` (any text file of at least 40 lines, after a successful `replace_lines`, `insert_after`, `edit_file`, `append_file` or `write_file`): the lines the edit wrote (the file minus the unchanged head and tail it shares with its earlier state) are compared as 8-line grams (blank and bracket/quote/comment-only lines skipped; grams where 60 percent of the lines are shorter than 12 characters ignored) with the rest of the file in one O(n) dict pass; the longest verbatim run found elsewhere adds ONE line `WARNING: the n lines you just wrote at a-b duplicate lines c-d that are still in the file. ...` to the result (also on a syntax-gate failure). Advice only, never a gate. A single region per edit: a multi-hunk `edit_file` is judged over the span of its first to last change. (3) `replace_lines` size sanity: more than 3x the replaced lines, a range under 10 lines and a replacement that contains the (non-trivial) line right after the range -> `NOTE: your replacement re-includes the line that follows the range (...) - check the end line.` Final gate: a duplicate binding is a static error (the static gate cap of 2 nudges applies); when the nudges are spent the answer goes out as `NOT VERIFIED: duplicate definition: <file> (<name>)`. Not shown in the VERIFIED STATE. Tests: `tests/test_codeagent_duplicates.py` (with the real before/after files of the incident in `tests/data/duplicate_incident/`).

**Edit protocol for prose-heavy files** (own design, no upstream). Measured live: rewriting 687 lines of dialogue prose in ranged parts took 10 minutes and changed 21 lines; the time went into edit-protocol friction, not into writing. Three deterministic behaviours, no model call (`tools.py` `replace_lines` / `edit_file` / `insert_after`, helpers in `edits.find_applied` and `symbols.shifted_starts`):
1. **ALREADY APPLIED.** The model re-sent an edit it had already applied (3-4 times in a row): first `NOT CHANGED ... not the lines you saw` (it used the stamp of the text from BEFORE its own edit), then `no change: ... identical` over and over. Now, when a `replace_lines` call is stale, outside the file or identical, the tool checks whether the NEW text already stands within 60 lines of the requested range (first and last line equal after whitespace folding, whole block >= 0.98 similar, at least 12 characters of content so a blank line or a brace never counts); `edit_file` does the same when its search text is gone or the edit changes nothing (every replacement of at least 30 characters must stand exactly once). The answer is ONE message: `ALREADY APPLIED: these lines already contain your new text (lines X-Y). Nothing to do here. Next line of your window that is still unchanged: N.` N comes from the stage cursor (`CodeEngine._next_unchanged`, the ranged part's window), else it is the line after Y; a finished window says so. The text never varies between repeats, so the loop guard counts a re-sent edit as a repeat and the ladder (note, nudge, stop) still works; it is not an error and `lookact` counts it as a look. The old `no change: the new lines are identical to the old ones.` message of `replace_lines` is gone (the same condition now answers ALREADY APPLIED); `edit_file` keeps its `no change` message when the replacement cannot be found in the file.
2. **Auto-relocate a stale stamp.** Earlier edits shift the lines, so a stamp (`expect=#hash`) goes stale although the block is intact. When the stamp does not match the requested range but matches EXACTLY ONE position within 80 lines (same block length, same content), `replace_lines` applies the edit there and says `applied at lines X-Y (the file had shifted by +k since you read it)`. Two matching positions, none, or a call without a stamp are rejected as before (`NOT CHANGED` with the current lines). `insert_after` is not relocated (a single-line stamp is too ambiguous).
3. **Syntax-break reject** (`coding.syntax_reject`, default `true`). A range edit at the edge of a block (4 times in 7 minutes) left the file broken until the model noticed `SYNTAX GATE FAILED` and repaired it. Now `replace_lines`, `edit_file` and `insert_after` parse the file before and after (py, json, toml; yaml when PyYAML is importable; the stdlib parsers only, not `coding.check_cmd`). If it parsed before and would not parse after, nothing is written and the answer is `NOT APPLIED: this edit would break the syntax of <file> (<error>). Your replacement text would leave these lines around the error: ... The file is unchanged. Re-send the edit with the correct range or complete block ...`; the proposal is kept in `.scratch/unsaved/<file>.<n>.txt` (n counts up, nothing is overwritten) and counts as a look. A file that was ALREADY invalid is edited as before (written, `SYNTAX GATE FAILED`). `write_file`, `append_file` and `apply_patch` are unchanged and still write a broken result with the gate message: use `apply_patch` (or set `coding.syntax_reject: false`) for a multi-step refactor that needs a temporarily broken state; the NOT APPLIED message says so. Why a gate and not advice: a broken file blocks every test and the model only sees the error after the next call, while a rejected edit costs one call and leaves the file usable.
Tests: `tests/test_codeagent_editproto.py`.

## Prose pipeline (`coding.prose_model`)

With `coding.prose_model` set, the agent gets a `write_prose(request, style_hint, max_words)` tool and one extra sentence in its system prompt telling it to use the tool for graphic or mature narrative passages (deaths, violence) instead of writing them itself. The tool asks the separate small text model for one passage (plain `llm.chat`, `background=True`, think off, CPU-only unless `prose_gpu`), using a fixed fiction-writer system prompt plus up to 3000 chars of style samples from the first existing of `STYLE.md`, `.agent/style.md`, `docs/STYLE.md` in the repo root. The passage comes back between `PASSAGE START` / `PASSAGE END` lines with a footer; the coding model copies it into the game file with its edit tools, and the usual marker guard still applies. Think blocks, "Here is..." lines, quotes, fences and harness markers are stripped; a refusal gets a fixed fallback message (event `prose_refused`) and a failure or timeout a short error string (event `prose_error`), never an exception. Try it without the agent: `agent code prose "the miller drowns in the weir" [--model M] [--gpu]`. Enable it in config.yaml with `coding:` -> `prose_model: gemma2:9b`.

## `tui_smoke` (curses / TUI / terminal games)

Seen live: asked to test a curses snake game, the model wrote a fake-screen script (its own renderer standing in for `curses`) twelve times with the same result and the loop guard ended the run (`loop_abort`). `run` gives a program no terminal (stdin is a pipe or `/dev/null`), so `curses.initscr()` fails and a fake screen looks like the only way. `tui_smoke` removes the reason: it runs the program in a REAL terminal and returns the screen as text.

    tui_smoke(command, keys=[], size="80x24", expect=[], timeout=10, settle_ms=300)

- `command`: a plain command is split with shlex and exec'd; anything with shell syntax (`&&`, pipes, redirects, `VAR=x`, globs) goes through `bash -lc` like `run`. Working directory is the repo root.
- `keys`: tokens sent one by one; after each one the call waits until the program's output was quiet for `settle_ms` (at most 2 s per key - an animated program never goes quiet), not for a guessed sleep. Names, any case, optionally in `<angle brackets>`: `Enter Esc Tab Space Backspace Delete Insert Up Down Left Right Home End PageUp PageDown Shift-Tab F1`..`F12 Ctrl-<x>` (also `C-x`, `^X`, `Ctrl-Space`, `Ctrl-[`) `Alt-<x>`; `wait:<ms>` (or `wait:1s`, at most 5 s) waits; `text:<literal>` types the text even when it is a key name (`text:Enter`); every other token is typed as text (`"hello"`, `"q"`; a newline inside text is Enter). Arrow keys, Home and End follow the program's cursor-key mode: `ESC O A` after the program sent `CSI ? 1 h` (curses `keypad(True)` does), else `ESC [ A`. The first keys wait for the program's first output (up to 2.5 s).
- `expect`: plain substrings (case-sensitive) or `re:` regexes (multi-line). Each is looked for on the final screen, on every settled screen of the run (initial, after each key) and in the main-buffer transcript; the answer says where it was seen. So "the title appeared, then the program quit" works even though the title is gone from the final screen. While an expectation is still open after the last key the call polls the screen until it appears or the timeout hits.
- The answer (at most `coding.tui_smoke_max_chars`, default 3500): `exited with code N` / `still running after the last key (stopped by the harness)` / `KILLED BY TIMEOUT` / `KILLED: more than 2 MB of output`; loud `!!` lines for a non-zero exit, a traceback or crash message and keys that were never sent because the program ended; `expect: 2/3 PASS` with one PASS / FAIL line each; `cursor at (row,col)`; the final screen (rows right-stripped, no blank rows after the content; a screen that does not fit keeps its top and bottom rows); for a program that left the alternate screen the last full-screen frame; and for a program that exited the last 15 lines of the main-buffer transcript, where a traceback lives (curses restores the main screen first). A line-based program (no cursor addressing, no alternate screen) is labelled as such, which is also how a fake screen shows up.
- Policy is the one of `run`: the command goes through the path jail, the temp-dir ban, the deny list and the safety classifier (`engine.decide` treats `tui_smoke` like `run`: same approvals in every mode), the protected files (`coding.protect`, read-only files) are snapshotted before and restored afterwards, a protected file the program creates is deleted again, files it changed are recorded like a shell write. It is an ACT in `lookact` (like `run`). In the loop guard its family is `tui <program> <files>`, so twelve smoke tests of `snake.py` with different keys are one family (note at 5, segment ends at 8) and identical calls hit the repeat ladder.
- Registration and prompt: the tool is always registered (description under 60 words). The system prompt gets ONE sentence about it only when a top-level `.py` file of the repo imports `curses`, `textual`, `urwid`, `pygame`, `prompt_toolkit` or `blessed` (checked once at session start); otherwise the prompt is unchanged.
- Check kind `tui` (`add_check`): `{command, keys, expect, size, timeout, exit_code}` runs through the same function at every final gate and before `mark_done` of its items, so "the game starts, shows the title, quits cleanly on q" is measured by the harness. Pass = every expect seen, no crash / traceback / timeout / output cap, and exit code 0 or still running; `exit_code=N` requires the program to have exited with N. The check runs only if the repo policy would run the command without asking (like a `command` check). Spec needs `command` and `expect` and/or `exit_code`.
- Headless games: for ALL `run` and `tui_smoke` executions `SDL_VIDEODRIVER=dummy` and `SDL_AUDIODRIVER=dummy` are set unless the user's environment already sets them; `DISPLAY` is neither required nor touched (the dummy driver opens no X connection). `tui_smoke` also sets `TERM=xterm-256color`, `COLUMNS`, `LINES`, `PYTHONUNBUFFERED=1`, a UTF-8 `LC_ALL` when none is set, and never sets `NO_COLOR` or `CI`.

How it works (`agent/codeagent/tuismoke.py`, stdlib only): `os.openpty()` with the window size set by `TIOCSWINSZ`; the command is started through a tiny `python -I -S -c` wrapper that makes the slave the controlling terminal (`TIOCSCTTY` on fd 0) and then `exec`s it. Why that way: `Popen(start_new_session=True)` alone gives a session WITHOUT a controlling terminal (`/dev/tty`, `getpass` and some curses setups then fail), `preexec_fn` could do the ioctl but is unsafe in the threaded engine process, and `pty.fork` forks the multi-threaded interpreter; the price is one extra interpreter start (~20 ms). The output goes through `Screen`, a VT100/xterm subset: cursor movement (`A B C D E F G H f d`), erase (`J K`), insert/delete (`L M P @ X`), scroll region (`r`) and scrolling (`S T`, reverse index), `ESC 7/8` and `CSI s/u`, alternate screen (`?47 ?1047 ?1049`) with its own buffer, `ESC ( 0` line drawing mapped to box characters, wide characters by `unicodedata.east_asian_width`, incremental UTF-8; SGR is parsed and ignored; unknown sequences are dropped by a small state machine that cannot wedge. Queries are answered so TUIs do not wait: cursor position (`CSI 6n`), device attributes (`CSI c`, `CSI > c`), status (`CSI 5n`), text-area size (`CSI 18 t`), DEC mode request; the kitty keyboard query (`CSI ? u`) is deliberately not answered (no reply means "unsupported"). At the end the whole process group gets TERM, then KILL, the leader is reaped, so nothing outlives the call; more than 2 MB of output stops the program. `pyte` is not used.

Getting the model to use it (measured: on a crashing curses game the one-sentence hint WAS in the system prompt and the model made 0 `tui_smoke` calls in 49 steps; it wrote its own screen-faking / logic-driving scripts and "proved" a symptom patch - a `try/except` that swallowed the off-screen GAME OVER banner, so the banner was never drawn any more - which `tui_smoke` showed at once):

- Prompt (only for a repo whose top-level `.py` imports a terminal library): two short sentences - terminal / curses / game programs cannot be run with `run` (no terminal), test them with `tui_smoke(command, keys, expect)`; to prove a fix make `expect` contain the text the player must SEE (the game over banner), not only that nothing crashes. The tool description and the `add_check` description say the same; for such a repo `add_check` opens with "For terminal programs prefer kind=tui." (decided when the tool list is built, so the repo must already contain the file at session start).
- Run-time redirect (`agent/codeagent/tuihint.py`, called at the end of `run`, no model call, only for `run` - never for `tui_smoke`): (a) `python3 file.py` / `python3 -m mod` (one level, simple command) whose source imports curses / textual / urwid / blessed / prompt_toolkit / pygame AND whose output shows the missing terminal (`setupterm`, `nocbreak() returned ERR`, `Redirection is not supported`, `not a tty`, `Inappropriate ioctl for device`, `curses.error`); (b) a heredoc / `-c` / stdin / file script that fakes a screen (a Fake/Mock/Dummy/Stub screen class together with `getmaxyx`, or a patched `curses.wrapper` / `initscr`). The result gets one line: "This is a terminal program. Use tui_smoke(command=..., keys=[...], expect=[...]) instead of faking a screen ..." - once per program (and once for fake screens), afterwards only "Terminal program: use tui_smoke(command, keys, expect)." For (a) the program is ALSO run once through `tui_smoke` (no keys, 3 s) and the screen appended under "tui_smoke (automatic, no keys, 3 s timeout):", so the model sees what the program shows. Not run automatically: a command with a pipe, redirection or `tee`, a fake-screen script, a repeat of the same program, or a command the repo policy would not run without asking (the same test as for `command` / `tui` checks, `_allowed_without_asking`; a denied or declined `run` never reaches this point). The automatic run has the protect snapshot and file-change notes of `tui_smoke`. Tests: `tests/test_codeagent_tuihint.py`.

Limits and pitfalls: colours and reverse video are not shown (SGR is ignored), so a highlighted menu entry is invisible - ask for text cues (a `>` marker) in the program under test; timing-dependent programs (animation, random events) give a different screen each run unless seeded (`--seed`, `PYTHONHASHSEED`); the slave keeps echo on until the program changes it (typed text may appear twice in a line-based program, as in a real terminal); a screen that never goes quiet is read after at most 2 s per key; the program sees `xterm-256color`, so a machine without that terminfo entry breaks curses (the same as in a terminal); no resize step, no mouse. Only top-level `.py` files trigger the prompt sentence. Tests: `tests/test_codeagent_tuismoke.py` (a real pty on Linux; a tiny curses game, a crash, a program that waits forever, application cursor keys, `CSI 6n`, alternate screen, line drawing, wide characters, the output cap, the policy, the family guard, the `tui` check).

### Tests the standard way (`agent/codeagent/stdpytest.py`)

Measured on a real run: a model-built 3-module CLI had `tests/test_*.py` doing `from models import Book`. They passed with `python -m pytest` (the harness' command puts the cwd on `sys.path`), but a user typing plain `pytest` got 3 collection errors, `ModuleNotFoundError: No module named 'models'`, and nobody noticed. After the tui gate, `_classic_gates` runs plain `pytest -q --collect-only` once (same `_exec` path, timeout and process group as the other harness runs; `pytest` or the interpreter's pytest without the cwd entry, else `uv run --no-project --with pytest pytest`) when a `.py` file was edited in this prompt / stage, the test command is a `python -m pytest` form, test files live below the root and nothing fixes the import path (skipped when there is a root `conftest.py`, `tests/__init__.py`, a `tests/conftest.py` touching `sys.path`, or `pythonpath` / `rootdir` in `pytest.ini`, `tox.ini`, `setup.cfg` or `pyproject.toml`). Only a bare-run `No module named '<m>'` where `<m>` is a top-level `.py` / package of the repo AND a `python -m pytest --collect-only` that does not fail the same way counts; both failing alike is another problem and no finding. The finding sends the model back once (cap 1): "Plain `pytest` fails with ModuleNotFoundError: <m> because the project root is not on sys.path ... add a conftest.py (one comment line is enough) in the project root or a pytest.ini with `pythonpath = .`; then both `pytest` and `python -m pytest` must pass."; if it persists the answer goes out as `NOT VERIFIED: tests only pass with python -m pytest: plain pytest fails to import <m>`. `verified.build` shows one line in the TESTS section (`plain pytest: FAILS (import path)`) that disappears once fixed. The result is cached on a content stamp of the python sources, test files and pytest config (event `std_pytest`, nudge event `std_pytest_nudge`). Tests: `tests/test_codeagent_stdpytest.py` (fake runner for the logic, one real pytest process).

### Crash gate (harness-run `tui_smoke`, `agent/codeagent/tuigate.py`)

Measured on real runs: a model-built curses snake CRASHED every time the snake died (the GAME OVER banner was wider than the grid, `curses.error`) and neither the model nor its own tests noticed, because its scripts drove the game LOGIC, never the real screen; when the model later "fixed" it, the fix silently skipped drawing the banner. The model does not reliably choose `tui_smoke`, so the final gate runs it itself (no model call).

- When: in `_classic_gates`, after the syntax / static / verify gates, if the repo is a terminal program (`tuismoke.repo_uses_tui`) and at least one project `.py` file (no tests, no scratch) was really edited in this prompt / stage. Skipped silently without an entry or with `coding.tui_gate: false`.
- Entry: a top-level `.py` with an `if __name__ == "__main__"` guard that imports curses / textual / urwid / blessed / prompt_toolkit / pygame (itself, or through one top-level module it imports); a file edited in this prompt wins, then the newest by mtime; `coding.tui_entry` overrides. Command: `python3 <entry>`.
- Play: three runs through `run_smoke`, all with `CodeTools._smoke` (the protect snapshot / restore of save files, file-change notes): two at 80x24 and one at 40x12 (small terminals crash many TUIs). Keys: up to 30 (12 for the small run) drawn from `Up Down Left Right w a s d Space Enter p r`, each followed by `wait:60..200` ms, as many as fit into `tui_gate_seconds` (8; half for the small run), then `Esc`, `q`, `Ctrl-C`. The seed is a hash of the entry's content, so the same code plays the same game and a failure can be reproduced; the failure text lists the keys. A typical tiny game takes about 14 s in total (measured: 3 runs, safe snake).
- FAIL: a traceback / crash message (main-buffer transcript or screen), a non-zero exit after the closing keys, or a program that printed nothing at start-up and had to be killed. `KeyboardInterrupt` from the closing Ctrl-C and exit 130 / SIGINT are not crashes. A program still running after the closing keys is only a WARNING (many games ignore `q` while playing) and is stopped quietly. The first failing run ends the gate.
- Result line: `TUI SMOKE: pass (3 runs, 14 s)`, optionally `- WARNING: ...` / `- NOTE: ...`, or `TUI SMOKE: FAIL - <exception line>` followed by the run size, the keys, the traceback excerpt and the last screen (at most ~1400 characters).
- On FAIL the model is sent back: "Your program crashed when played with random keys. Reproduce with tui_smoke and fix the cause (not by hiding the error)." plus the compact failure. It counts like the other gate nudges (the consecutive-gate rule, a per-gate cap of 2); then the answer goes out as NOT VERIFIED: `program crashes under random play: <line>`. The same code is never played twice: the result is cached on a content stamp of the edited `.py` files and the entry, so a text-only answer repeats the cached failure (and counts) until a real edit happens (event `tui_gate`, `cached: true`).
- Policy: the command must be one the repo policy would run without asking (jail, deny list, temp-dir ban, classifier - `_allowed_without_asking`, like `tui` checks); otherwise the gate is skipped with the note `TUI SMOKE: skipped (the repo policy would ask ...)`. A save file the program writes is restored like after `tui_smoke`.
- Visible text: when an edit ADDED a string literal containing GAME OVER, Game over, You died, Press any key or Victory (or a `coding.tui_banner_words` entry; case-insensitive, string literals only - not comments or other phrases) and that text never showed on any settled screen (or in the transcript) of the three runs, the result line gets a NOTE: `The text "GAME OVER" exists in the code but never appeared on screen in the random-play runs - check that the player can actually see it.` It never blocks (random play often does not reach the end of a game).
- Where it shows: the console, `verified.build` (a `TUI SMOKE` section, the gate's cached result - not re-run by `/state`; `build(engine, run_tui=True)` plays again) and the autopilot report (`## tui smoke`; a FAIL is also listed under NOT VERIFIED).
- Tests: `tests/test_codeagent_tuigate.py` (real ptys and tiny curses programs: the banner-wider-than-the-grid crash, a safe banner, a swallowed error, a crash only at 40x12, a program that ignores `q`, caching, the cap, the policy, protect).

## Output cap and sprawl guard

`coding.num_predict` is 8192 tokens (~27 KB of code in one call; it was 16384). Measured: a real run's step 2 was one generation of ~16000 tokens that ran into the limit - about 5 minutes at 54 tok/s - so the cap now loses at most ~2.5 minutes; bigger files go in parts (`write_file`, then `append_file`). A reply that ends with `done_reason: length` NEVER runs a call - not a whole one, not a half-written one - and the model gets: "Your reply was cut off after N tokens and nothing ran: write the file in several smaller write_file/append_file calls of at most ~150 lines each ..." (event `cut_off`).

Sprawl guard (`agent/codeagent/sprawl.py`, fed by every streamed piece, which stands for one token): past `coding.sprawl_tokens` (6000) tokens of one generation with no tool call (JSON object, `<tool_call>` / `<function=` block) or code fence open, or closed within the last `coding.sprawl_quiet` (2000) tokens, the stream is aborted through the existing abort path (`GenerationAborted`, event `gen_sprawl`, counted like an empty reply: six in a row end the segment as error) and the model gets the same smaller-steps instruction. A call that is being written counts as activity while it is open, so a legitimate 7000-token `write_file` is only ever stopped by the hard cap. Thinking tokens count towards the length and never as structure. Native tool calls arrive in one piece at the end (Ollama buffers them), so for those only the token cap applies.
